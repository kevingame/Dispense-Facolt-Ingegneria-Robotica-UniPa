Formulario — solo formule

Solo formule, per consultazione rapida ed esercizi · basato sulla dispensa del corso (Prof.ssa A. De Paola, UniPa).

⚠ Regola d'oro sulle unità — leggere prima di ogni esercizio
1. Dimensioni dei dati (File, MSS, MTU, payload, header/overhead) → si usano potenze di 2:
  1 KB = 1024 B  ·  1 MB = 1024 KB = 1.048.576 B  ·  1 B = 8 bit

2. Velocità/tassi di trasmissione (R, banda del link, throughput, goodput) → si usano potenze di 10:
  1 kbps = 10³ bps  ·  1 Mbps = 10⁶ bps  ·  1 Gbps = 10⁹ bps

3. Prima di dividere due grandezze, portale sempre alla stessa unità. Il caso più comune è N = File/MSS: se File è dato in KB/MB e MSS in byte, va prima convertito il File in byte (·1024 o ·1024²), non il contrario.
Es.: File = 2,5 KB, MSS = 256 B  →  File in byte = 2,5 · 1024 = 2560 B  →  N = 2560 / 256 = 10 pacchetti.

4. Per i tempi di trasmissione (T = L/R) L va in bit e R in bps: se una dimensione è data in byte, moltiplicarla ×8 prima di dividere per R.

1. Ritardi e trasmissione

Tempo di trasmissione
Ttrasm = L / R
L in bit, R in bps. Se L è dato in byte, moltiplica ×8; se R è dato in Mbps/Gbps, moltiplica ×10⁶/×10⁹ per averlo in bps.
Tempo di trasmissione (con overhead)
Ttrasm = MTU · 8 / R   con   MTU = MSS + overhead
MSS è il payload (dati utili del segmento, senza header), MTU è la dimensione totale realmente trasmessa sul link (payload + overhead/header). Quindi Ttrasm = (MSS + overhead) · 8 / R è la stessa cosa scritta in termini di MSS invece di MTU. Se le dimensioni sono in byte, ·8 converte in bit; se R è in Mbps ricorda 1 Mbps = 10⁶ bps.
Es.: MSS = 256 B, overhead ≈ 0 → MTU = 256 B, R = 200 Mbps  →  L = 256·8 = 2048 bit; R = 200·10⁶ = 200.000.000 bps  →  Ttrasm = 2048/200.000.000 = 1,024·10⁻⁵ s = 0,01024 ms.
Ritardo di nodo
dnodo = dproc + dqueue + dtrans + dprop
elaborazione + accodamento + trasmissione + propagazione
Ritardo di propagazione (Tprop)
Tprop = d / Vp
d = lunghezza del collegamento fisico (in metri), Vp = velocità di propagazione del mezzo (tipicamente ≈ 2,8·10⁸ m/s in rame/fibra). Dipende solo dalla distanza, non dalla banda del link né dalla dimensione del pacchetto.
Es.: d = 100 m, Vp = 2,8·10⁸ m/s  →  Tprop = 100/2,8·10⁸ = 3,57·10⁻⁷ s ≈ 0,357 μs.
RTT (caso semplice, solo propagazione)
RTT = 2 · Tprop
tempo di andata e ritorno di un bit tra due host direttamente connessi (nessun accodamento/elaborazione)
Intensità di traffico (queuing)
I = L·a / R
a = tasso arrivo pacchetti; I≈0 poco ritardo, I→1 ritardo cresce, I>1 ritardo infinito
Throughput end-to-end
Th = min(Rc, Rs, R/10)
collo di bottiglia tra client, server e core della rete
Store-and-forward (pacchetto di L bit, link R bps)
Per ricevere 1° pacchetto: 2L/R  ·  per N pacchetti in serie su k hop: T = k·L/R + (N−1)·L/R

2. Numero di pacchetti / frammentazione

Numero di pacchetti
N = ⌈Smess / PL⌉
Smess = dimensione messaggio (in byte), PL = payload utile per pacchetto (in byte). Se Smess è dato in KB/MB, convertilo prima in byte — vedi box unità sopra.
Es. (KB): Smess = 2 KB, PL = 536 B  →  Smess in byte = 2 · 1024 = 2048 B  →  N = ⌈2048/536⌉ = ⌈3,82⌉ = 4 pacchetti.
Es. (MB): Smess = 3 MB, PL = 536 B  →  Smess in byte = 3 · 1024 · 1024 = 3.145.728 B  →  N = ⌈3.145.728/536⌉ = ⌈5868,9⌉ = 5869 pacchetti.
Dimensione ultimo pacchetto
Slast = Smess − (N−1)·PL
Payload utile
PL = MTU − overhead
es. MTU 1500 B − 40 B header = 1460 B. PL è lo stesso concetto di MSS (il payload/dati utili): MTU = PL + overhead = MSS + overhead.
Conversioni comuni
1 kbps = 10³ bps = 1.000 bps  ·  1 Mbps = 10⁶ bps = 1.000.000 bps  ·  1 Gbps = 10⁹ bps
1 Byte = 8 bit  ·  1 KB = 1024 B  ·  1 MB = 1024 KB = 1.048.576 B
Dimensioni file/pacchetti/MTU/MSS → potenze di 2 (KB, MB). Velocità/banda/tassi di trasmissione (kbps, Mbps, Gbps) → potenze di 10. Non mischiare le due basi nello stesso calcolo.

3. Tempo di risposta / RTT

Tempo di risposta totale (richiesta oggetto singolo)
Trisp = 2·RTT + Ttrasm(file)
RTT include propagazione + accodamento + elaborazione (andata e ritorno)
RTT stimato (EWMA)
EstimatedRTT(t) = (1−α)·EstimatedRTT(t−1) + α·SampleRTT(t)
α tipico = 0,125
Deviazione RTT
DevRTT(t) = (1−β)·DevRTT(t−1) + β·|SampleRTT(t) − EstimatedRTT(t)|
β tipico = 0,25
Intervallo di timeout TCP
TimeoutInterval = EstimatedRTT + 4·DevRTT

4. TCP — finestra, throughput, goodput

Numero di segmenti
N = File(byte) / MSS(byte)
File e MSS devono essere nella stessa unità (byte) prima di dividere. Il File è quasi sempre dato in KB/MB (potenze di 2): convertilo in byte con ·1024 (KB→B) o ·1024² (MB→B). L'MSS è quasi sempre già in byte, non va convertito. Ricorda: MSS = payload (dati utili per segmento) = MTU − overhead, lo stesso PL già visto in sezione 2.
Es.: File = 5 kB, MSS = 512 B  →  File in byte = 5·1024 = 5120 B  →  N = 5120/512 = 10 segmenti.
Frequenza d'invio (regime)
freq. invio ≈ CongWin / RTT  [byte/s]
CongWin in byte, RTT in secondi → risultato in byte/s. Per confrontarlo con la banda del link (in bps) moltiplicare ×8.
Throughput
Throughput = Datitrasmessi totali·8 / Ttot
include anche le ritrasmissioni (dati "sprecati"). Dati in byte ×8 per avere bit, Ttot in secondi → risultato in bps (dividi per 10⁶ per i Mbps).
Es.: 11 segmenti da 256 B trasmessi in totale (con 1 ritrasmissione), Ttot = 1,58432 ms = 0,00158432 s  →  Throughput = (256·8)·11 / 0,00158432 ≈ 14.258.228 bps = 14.258.228/10⁶ ≈ 14,3 Mbps.
Goodput
Goodput = Datiutili (file)·8 / Ttot = N·MSS·8 / Ttot
solo dati utili consegnati (esclude ritrasmissioni). N·MSS = dimensione file in byte; ·8 converte in bit; Ttot in secondi → risultato in bps.
Es.: N = 10 segmenti utili, MSS = 256 B, Ttot = 0,00158432 s  →  Goodput = 10·256·8 / 0,00158432 ≈ 12.930.116 bps ≈ 12,93 Mbps.
Dilemma numeri di sequenza (GBN / SR)
dimensione finestra ≤ 2numero bit seq. ⁄ 2  (occorrono 2N sequenze con finestra N)

5. Indirizzamento IP / Subnetting

Indirizzo IP
32 bit → 4 ottetti in notazione decimale puntata (0–255).0–255.0–255.0–255
Prefisso di rete /n
n bit di rete, (32−n) bit di host
host disponibili = 2(32−n) − 2 (rete + broadcast esclusi)
AND bit-a-bit (indirizzo di sottorete)
Sottorete = Indirizzo AND Netmask
Broadcast = Sottorete OR (NOT Netmask)
Frammentazione IP — campo Spiazzamento (offset)
Spiazzamento = posizione del frammento nel datagramma originale (in byte) / 8
l'offset nell'header IP è espresso in multipli di 8 byte. Es.: datagramma di 4000 B, MTU = 1500 B (1480 B dati/frammento) → 2° frammento inizia al byte 1480 → Spiazzamento = 1480/8 = 185.

6. Instradamento — Link-State (Dijkstra) & Distance Vector (Bellman-Ford)

Equazione di Bellman-Ford
Dx(y) = minv { c(x,v) + Dv(y) }
costo minimo da x a y passando per il vicino v
Algoritmo di Dijkstra (Link-State) — passo di aggiornamento
D(v) = min( D(v), D(w) + c(w,v) )
w = nodo appena aggiunto a N' (con D(w) minimo tra i nodi non ancora in N'); v = nodo adiacente a w non ancora in N'. Complessità: O(n²) nell'implementazione semplice, O(n log n) in quella ottimizzata.

7. Crittografia

Cifratura simmetrica
Y = E(K, X)  ·  X = D(K, Y)
stessa chiave K per cifrare/decifrare
Numero di chiavi (simmetrica, N utenti)
N_chiavi = N·(N−1) / 2
Cifratura asimmetrica
Segretezza: Y = E(PUa, X)  →  X = D(PRa, Y)   |   Autenticazione: Y = E(PRb, X)  →  X = D(PUb, Y)
PU = chiave pubblica, PR = chiave privata

Si vuole trasmettere un messaggio di dimensione 3 MB attraverso la rete a commutazione di pacchetto schematizzata in figura (Host A — R1 — R2 — Host B). I 3 link sono lunghi rispettivamente 100 m, 50 m e 80 m, ed ognuno ha un'ampiezza di banda pari a 512 kbps e velocità di propagazione 2,8×10⁸ m/s. Nota: per le dimensioni dei file si usano potenze di 2; per i tassi di trasmissione potenze di 10.

Domande aggiuntive: (a) Dopo quanto tempo l'host B riceve interamente il primo pacchetto? (b) Dopo quanto tempo riceve interamente il secondo pacchetto? (c) Tempo totale per l'intero messaggio.

Come calcoliamo la dimensione dell'ultimo pacchetto?
Slast = Smess − (N−1)·PL = 3·2²⁰ − 5868·536 = 480 byte

Calcolo dei tempi di propagazione Tprop1,2,3, del tempo di trasmissione TTras, e risposte ai punti a) b) c).

Tprop2 = L2 / Vp = 50m / 2,8·108 m/s = 1,78·10-7 s ≈ 0,178 μs

TTras = (PL+OH)·8 bit / R = (536+28)·8 / 512 Kbps = 8,8125·10-3s ≈ 8,81 ms
a) Dopo quanto tempo l'host B riceve interamente il primo pacchetto?
TP1 = 3·TTras + (Tprop1+Tprop2+Tprop3) ≈ 26,43 ms
b) Dopo quanto tempo l'host B riceve interamente il primo pacchetto?
TP2 = TP1 + TTras

TTOT = Tprop1+Tprop2+Tprop3 + (N+1)·TTras + TTras,last ≈ 51,75 s

Esercizio 1

Un host, direttamente connesso ad un server tramite un canale privo di errori o perdite, richiede una pagina web statica, di dimensione 3 kB, contenente due immagini di dimensioni 50 kB e 80 kB rispettivamente. Nell’ipotesi che, subito dopo avere ricevuto i file richiesti, l’utente inoltri una seconda richiesta per la stessa pagina, e che il client web implementi una cache del web, qual è il tempo totale per lo scambio di file? Si supponga che il protocollo utilizzato sia HTTP/1.1; si assuma inoltre che il canale abbia RTT = 1 ms, ampiezza di banda pari a 10 Mbps ed MTU = 1500 byte e che l’overhead complessivo di pacchetto sia pari a 48 byte.
Note:
Per le dimensioni relative ai file si considerino le grandezze come potenze di 2 e quindi in particolare:
1 MB = 1.024 kB; 1 kB = 1.024 byte
Per le dimensioni relative ai tassi di trasmissione e alle ampiezze di banda si considerino le grandezze come potenze di 10 e quindi in particolare:
1 kbps = 1.000 bps; 1 Mbps = 1.000.000 bps

Esercizio 2

Data la configurazione schematizzata in figura, si assuma che l'host H richieda una pagina web al server www.ebay.com, costituita da un file HTML di 12 kB e dall'immagine www.foo.it/pics/img1.jpg di 4 MB, e che, successivamente, lo stesso host richieda una pagina web al server www.amazon.it, costituita da un file HTML di 10 kB e dall'immagine www.foo.it/pics/img2.jpg di 3 MB.
Assumendo che tutte le interazioni avvengano con HTTP/1.1 e che il server www.foo.it utilizzi cookie di 100 byte, si calcoli il tempo totale necessario ad ottenere le due pagine.
Si considerino tutti i collegamenti caratterizzati da ampiezza di banda di 200 Mbps, tempo di propagazione medio pari a 0,1 ms, MTU pari a 1500 byte e overhead di 40 byte.

$ svolgimento --verbose

06 CH.02 · 2.4

Traccia dell'esercizio

Un client visita per la prima volta la pagina web zappe.it/index.html. Questa pagina contiene al suo interno un'immagine ospitata su un server di terze parti, foo.it/img1.png. Dopo una settimana, lo stesso utente visita un sito di scarpe, scarpe.it/index.html, all'interno del quale è presente un banner ospitato sempre dal server di tracciamento foo.it/banners.gif.

Descrivere lo scambio di messaggi HTTP tra client e server, illustrando come il server foo.it utilizzi i cookie per tracciare l'utente attraverso siti differenti e fornire contenuti personalizzati.

$ svolgimento --verbose

Svolgimento e Analisi dei Messaggi HTTP Il protocollo HTTP è intrinsecamente senza stato (stateless). I cookie rappresentano un artificio tecnico che permette al server di ricordare le interazioni passate dell'utente. Tramite questo meccanismo, il server attribuisce un identificativo anonimo al client durante la prima interazione, e il client lo riutilizzerà in seguito per farsi riconoscere. Affinché funzioni, il server deve possedere un database dove salvare tutti gli identificativi assegnati.

Fase 1: Prima interazione (Client senza cookie su zappe.it)
  • Nella primissima richiesta verso foo.it, il client non invia alcun cookie poiché non gli è stato ancora assegnato.
  • Il client invia la richiesta iniziale per la pagina base a zappe.it, che risponde con il file HTML (200 OK) contenente il riferimento all'oggetto img1.png ospitato su foo.it.
  • Il client effettua quindi una richiesta al server di terze parti foo.it: 
    GET /img1.png HTTP/1.1
Host: foo.it
Connection: open
  • Il server foo.it riceve la richiesta, genera un nuovo identificativo (ad esempio 1518), lo memorizza all'interno di un proprio database associandolo al profilo dell'utente e invia la risposta includendo l'header Set-Cookie: 
    HTTP/1.1 200 OK
Connection: open
Content-Length: 5786
Content-Type: image/png
Set-Cookie: 1518
Fase 2: Seconda interazione (Dopo una settimana su scarpe.it)
  • L'utente visita il sito scarpe.it/index.html a distanza di una settimana.
  • Il browser incontra un nuovo riferimento al server foo.it all'interno della pagina, questa volta per il file banners.gif.
  • Poiché il client possiede già l'identificativo rilasciato da foo.it (che funge da cookie di terza parte per il tracciamento incrociato), lo include automaticamente nella nuova richiesta HTTP verso quel dominio: 
    GET /banners.gif HTTP/1.1
Host: foo.it
Connection: open
Cookie: 1518
  • Il server foo.it legge l'header Cookie: 1518 e consulta il proprio database per risalire allo storico della sessione dell'utente, sapendo che aveva già visitato zappe.it in precedenza.
  • Riconoscendo il profilo dell'utente, il server elabora una risposta mirata, proponendo ad esempio una pubblicità personalizzata come "un dondolo da giardino".

07 CH.02 · 2.5

Esercizio 7

Data la configurazione indicata in figura, si supponga che l'utente marco.rossi@unipa.it spedisca una email contenente un testo di 4 KB e un allegato di 100KB agli utenti piero.neri@unipa.it e carlo.verdi@gmail.com. Si calcoli il tempo necessario alla trasmissione della email fino alla ricezione, assumendo che non vi siano tempi morti tra le due fasi e che i destinatari utilizzino entrambi il protocollo POP3. Si assuma che la LAN-UNIPA e tutti i link siano caratterizzati dalle seguenti caratteristiche: un'ampiezza di banda pari a 100 Mbps, un tempo medio di propagazione pari a 1 ms, MTU 1500 byte e che l'overhead complessivo di pacchetto sia pari a 48 byte.

$ svolgimento --verbose

Dati e calcoli preliminari:

Dimensione Email + Allegato = 4 KB + 100 KB = 104 KB = 104 · 1024 = 106.496 byte
Banda = 100 Mbps = 108 bps
Tprop = 1 ms per ogni singolo link
MTU = 1500 byte, Overhead = 48 byte

Payload per pacchetto = 1500 - 48 = 1452 byte
Npack_tot = ⌈106.496 / 1452⌉ = 74 pacchetti
Lbit = 1500 byte · 8 = 12.000 bit
Ttrasm_1_pack = 12.000 / 108 = 0,00012 s = 0,12 ms
Dimensione Tot = 74 pack · 1500 = 111.000 byte
Tempo Trasmissione intera email (Ttrasm_tot) = (111.000 · 8) / 108 = 0,00888 s = 8,88 ms

Fase 1: Marco -> mail.unipa.it (SMTP)
Attraversa solo la LAN (Tprop = 1 ms). Nessun router intermedio per l'accodamento.
T1 = 12(Tprop) + (Tprop + Ttrasm_tot) + 3(Tprop) = 12(1) + (1 + 8,88) + 3(1) = 12 + 9,88 + 3 = 24,88 ms

Fase 2: mail.unipa.it -> mail.google.com (SMTP)
Attraversa LAN, L1, L2 (Tprop_tot = 1 + 1 + 1 = 3 ms). Ci sono 2 router di mezzo (R1 e R2), che aggiungono tempi di ritrasmissione/accodamento del primo pacchetto.
T2 = 12(Tprop_tot) + (Tprop_tot + 2(Ttrasm_1_pack) + Ttrasm_tot) + 3(Tprop_tot)
T2 = 12(3) + (3 + 2(0,12) + 8,88) + 3(3) = 36 + 12,12 + 9 = 57,12 ms

Fase 3: Ricezione piero.neri (POP3 da mail.unipa.it)
Attraversa solo la LAN (Tprop = 1 ms).
T3 = 11(Tprop) + (Tprop + Ttrasm_tot) + 2(Tprop) = 11(1) + (1 + 8,88) + 2(1) = 11 + 9,88 + 2 = 22,88 ms

Fase 4: Ricezione carlo.verdi (POP3 da mail.google.com)
Attraversa L3 e L2 (Tprop_tot = 1 + 1 = 2 ms). C'è 1 router di mezzo (R2).
T4 = 11(Tprop_tot) + (Tprop_tot + 1(Ttrasm_1_pack) + Ttrasm_tot) + 2(Tprop_tot)
T4 = 11(2) + (2 + 0,12 + 8,88) + 2(2) = 22 + 11,00 + 4 = 37,00 ms

Tempo Totale Finale:
Poiché le operazioni di ricezione avvengono in parallelo sui due server, il tempo totale per far sì che la mail giunga a *tutti* i destinatari è dettato dal percorso più lungo (ovvero quello verso Carlo):
Ttotale = T1 + T2 + T4 = 24,88 + 57,12 + 37,00 = 119,00 ms
